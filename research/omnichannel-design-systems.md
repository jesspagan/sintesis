# Omnichannel design systems

Produced 2026-08-04 via web search and direct fetches of the W3C Design Tokens Community Group (DTCG) spec, Style Dictionary and Deutsche Telekom Scale primary docs, an Adobe official blog post, and a Nielsen Norman Group (NN/g) article; a claim about IKEA's Skapa system rests on a single secondary recap of a practitioner talk (flagged below). No prior memo in this repo covers design systems as a UX/product discipline — this is a new topic area, not an extension of the orchestration/tooling memos.

**how to apply:** consult when scoping or evaluating a design system that's expected to span more than one platform or physical/digital channel — to know what token tooling can and can't carry across channels, which governance model fits, and which "omnichannel" claims are marketing versus substantiated.

## 1. Definition, and how it differs from "multi-platform"

An omnichannel design system is a single design language and (usually) token pipeline intended to produce a *continuous* experience across every touchpoint a customer or user might move through — not just multiple platforms of the same kind (web + iOS + Android) but qualitatively different channels: physical retail, kiosks, ATMs/branches, print, email, and voice/conversational interfaces. This is broader than a "multi-platform" design system (e.g., a component library that ships to web, iOS, and Android) and broader still than a "multi-brand" one (theming the same components for different brands) — an omnichannel system can need all three simultaneously.

NN/g's "Consistency in the Omnichannel Experience" ([nngroup.com](https://www.nngroup.com/articles/omnichannel-consistency/), published 2016, still NN/g's standing guidance) frames the goal around three things that must stay consistent, not just visual style: **core functionality** (workflows behave the same so users can transfer learned knowledge between channels), **customer data** (real-time synchronized state — "to customers, you are one company; they don't draw dividing lines between channels like organizations do"), and **visual design** (unified palette, imagery, language). Its explicit caveat: consistency and per-channel optimization are in tension, and "it's vital for organizations to understand when it's okay to compromise consistency in order to provide an appropriately optimized experience" — i.e., omnichannel is not "identical everywhere," it's "recognizably the same, tuned per channel."

## 2. Token architecture: what it actually carries across channels

The technical backbone of a modern design system is **design tokens** — named, platform-agnostic values (color, spacing, type scale, etc.) transformed at build time into each platform's native format. Two things ground this:

- **W3C Design Tokens Community Group (DTCG)** format spec — as of the fetch date this is still a *Draft Community Group Report* ("Do not attempt to implement this version... do not reference this version as authoritative in any way"), not a finished W3C Standard, though industry coverage reports a first "stable" editor's draft milestone around October 2025 ([designtokens.org draft](https://www.designtokens.org/tr/drafts/format/); [designzig.com](https://designzig.com/design-tokens-specification-reaches-first-stable-version-with-w3c-community-group/)). It defines primitive types (color, dimension, font family/weight, duration, cubic-bezier, number) and composite types (border, shadow, gradient, typography, transition). Its worked platform conversions are screen-only — `px`→`dp` (Android) / `pt` (iOS), `rem`→`sp` — it does not define conversions for print (CMYK/Pantone), signage, or voice output.
- **Style Dictionary** is the de facto build tool implementing this idea: a single token source transforms into CSS custom properties, SCSS, iOS Swift, Android XML, etc., with unit conversion per platform baked in (e.g., `16px` → `1rem` for CSS, `16dp` for Android, `16pt` for iOS) ([styledictionary.com](https://styledictionary.com/), [GitHub](https://github.com/style-dictionary/style-dictionary)). Its own multi-platform examples cover web/iOS/Android combined with multi-*brand* theming — not print, kiosk, or voice output formats.
- Design tokens as a concept originated at Salesforce: SLDS built the open-source **Theo** tool specifically "to scale design systems across multiple platforms and devices," letting the same token feed CSS/Sass variables on web and JSON/YAML on native apps ([search synthesis, corroborate before citing as sole source]). SLDS 2 has since shifted toward CSS custom properties directly and reduced reliance on the token abstraction layer.

**Net finding:** the token pipeline that "omnichannel design system" marketing implicitly invokes is mature and standardizing for *screen-based* platforms (web, iOS, Android, sometimes desktop/XR). It does not yet have a standardized bridge to print, physical signage/packaging, or voice — those remain governed by traditional brand-guideline documents (Pantone/CMYK specs, printer-ready templates) maintained separately from the code-facing token pipeline, per generic brand-guideline sources surveyed. Voice/conversational interfaces are their own discipline with a distinct technical stack (ASR → NLP → dialog management → TTS) and a distinct design practice ("conversation design," combining VUI, interaction, motion, and UX writing); no case study surfaced of a token system feeding voice-output styling (tone, pacing, SSML equivalents) the way it feeds CSS. Treat "omnichannel" as strongest for digital-screen channels and weakest — usually just shared foundational values like brand color/type, manually re-applied — for print, physical, and voice.

## 3. Case studies

- **IKEA Skapa** is the clearest documented case of a token system explicitly spanning *non-screen-standardized* channels: reported as covering web, iOS, Android, in-store kiosks, internal tools, and email marketing, serving 200+ product teams, 400 Figma editors, 60+ components, and 400+ tokens with dark-mode support ([intodesignsystems.com recap](https://www.intodesignsystems.com/use-cases/ikea-design-system) of a talk by Skapa's Product Owner Caroline Dahl and Senior Designer Jonatan Grönkvist). **Confidence flag:** this is a single secondary source (a meetup site's recap of a talk), not a primary IKEA publication or the talk transcript itself — the scale/channel numbers should be treated as practitioner-reported, not independently verified.
- **Adobe Spectrum / Spectrum 2** — confirmed via Adobe's own blog: spans "web, desktop, mobile, and even mixed reality" across 100+ Adobe applications, with Spectrum 2 rolling out platform-specific variants (web/iOS first, then desktop apps like Photoshop/Lightroom/Premiere) rather than one identical component set everywhere — an explicit acknowledgment that "omnichannel" in practice means *coherent, not identical* ([blog.adobe.com](https://blog.adobe.com/en/publish/2023/12/12/adobe-unveils-spectrum-2-design-system-reimagining-user-experience-over-100-adobe-applications); [adobe.design](https://adobe.design/ideas/introducing-spectrum-2)).
- **Deutsche Telekom Scale** — primary GitHub README confirms multi-*brand* theming (an open-source neutral theme vs. the trademark-protected Telekom theme, swappable) and a design-token npm package (`@telekom/design-tokens`, superseding earlier per-theme token packages), but the README itself doesn't document channel coverage beyond web components (Stencil/TypeScript) — no confirmed evidence of the same reach into physical/voice channels that Skapa claims ([github.com/telekom/scale](https://github.com/telekom/scale)).
- **Banking sector** (DBS Bank, per secondary case-study coverage) is cited as an example of workflow continuity across app/ATM/branch — a customer can start a transaction on the app and finish it at an ATM or in a branch — illustrating the "core functionality + data consistency" legs of NN/g's framework more than the "visual design" leg, since ATMs/branches aren't running the same component library as the app.

## 4. Governance models

Practitioner sources (Design Systems Collective, SeaLab) converge on the same two-model framing used elsewhere for large systems: **centralized** governance (one team owns the system, strong consistency, bottleneck risk as product count grows) versus **federated** governance (ownership distributed across product teams, coordinated by a working group/guild, chosen once an organization has "multiple product lines with different UX needs" or has already hit the centralized bottleneck) ([gavinplatt.medium.com](https://gavinplatt.medium.com/federated-governance-how-to-scale-a-design-system-across-products-without-losing-control-f3000468ba41); [sealab.design](https://sealab.design/blog/design-system-governance/)). For multi-brand systems specifically, a hierarchical layering pattern is reported in enterprise case studies: a **foundational layer** sets brand-wide governance/consistency, while **implementation layers** give business-unit/domain teams scalability and local adaptation ([Design Systems Collective multi-brand case study](https://medium.com/design-bootcamp/building-scaling-a-global-enterprise-design-system-a-case-study-c90f3505dd1b)). Omnichannel scope tends to push toward federation by necessity — no single team plausibly owns web components, native app components, kiosk firmware, print production, and voice dialog design at once.

## 5. Where the "omni" claim tends to break down

Search results on omnichannel *failure modes* (not design-system-specific, but directly relevant) converge on a consistent critique: organizations frequently practice "channel-washing" — adding channels without redesigning the underlying journey — which multiplies inconsistency rather than resolving it, because the backend systems behind each channel were "never designed to share" a unified customer identity or context (per aggregated CX-industry commentary, e.g. [cxtoday.com](https://www.cxtoday.com/contact-center/omnichannel-strategy-scaling-broken-customer-experience/)). This corroborates NN/g's point from a different angle: a shared component library or token set (the design-system layer) does not by itself deliver the "customer data" consistency leg NN/g calls out as equally necessary — that requires backend/data integration a design system doesn't touch. **A design system can make an omnichannel experience look consistent while the underlying journey remains fragmented; the two are separable failures.**
