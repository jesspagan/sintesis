# Pre-commit review orchestration for agentic coding

Prepared 2026-07-11. Grounded in this repo's own `.claude/` config and the built-in Claude Code plugins installed in this environment (`~/.claude/plugins/marketplaces/claude-plugins-official/`), Anthropic's published best-practices docs and Code Review product page, and a web research pass across industry commentary (Addy Osmani, Port.io, DORA) and two 2026 papers on human review of AI-generated code.

**how to apply:** consult when designing or auditing the process a coding agent (this session or another) should follow between "changes are made" and "changes are committed/merged" — choosing among hooks, review skills/subagents, and human checkpoints.

## 1. Why this is a live problem, not a solved one

The bottleneck moved. Code generation got cheap; verification didn't. Addy Osmani frames it as agents producing "roughly four times the code for something like a tenth more delivered value" — reviewers can't keep pace, so PRs increasingly merge with thinner review than before ([Osmani](https://addyosmani.com/blog/agentic-code-review/)). DORA's 2025 report corroborates the mechanism from the other side: higher AI adoption correlates with higher throughput *and* higher delivery instability at the same time — the acceleration in writing code doesn't come with a matched acceleration in the practices (review, testing, QA) that used to catch mistakes before they shipped ([DORA — Balancing AI tensions](https://dora.dev/insights/balancing-ai-tensions/)). A second-order risk compounds this: a 2026 study, "Habituation at the Gate," finds that human reviewers' approval rates *rise* while their scrutiny *declines* the more AI-generated code they review — the human checkpoint itself degrades with repeated exposure unless something structural counteracts it ([arxiv.org/pdf/2606.22721](https://arxiv.org/pdf/2606.22721)). None of this means automated review is unwanted — Anthropic's own Code Review product cites catching a critical auth bug that human review missed — but it does mean "add an AI review step" isn't sufficient on its own; the process around it (what gates are deterministic vs. advisory, what always needs a human, how reviewer attention gets rationed) matters as much as the review itself.

## 3. Claude Code's own primitives for pre-commit review

Three mechanisms recur across Anthropic's docs and the installed plugins, in increasing order of enforcement strength:

- **Prose/skill instructions** (advisory). A skill or CLAUDE.md can *ask* for a review step, but nothing stops the model from skipping it under pressure or context loss. This is what this repo has today for anything beyond the four built-in review skills.
- **Subagent review** (a second opinion, not enforced). Anthropic's best-practices doc calls this "an adversarial review step": *"Before treating a task as done, have a subagent review the diff in a fresh context and report gaps... A reviewer running in a fresh subagent context sees only the diff and the criteria you give it, not the reasoning that produced the change, so it evaluates the result on its own terms."* ([Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)). The doc explicitly warns about over-trusting this: a reviewer prompted to find gaps will usually report *some*, even on sound work, so scope it to correctness/requirements findings and treat the rest as optional — a direct echo of the false-positive-filtering pattern the installed plugins implement mechanically (see §4). The same doc names a **Writer/Reviewer pattern**: run implementation and review in separate sessions/fresh contexts (Session A writes, Session B — with no memory of *why* A made its choices — reviews), because "a fresh context improves code review since Claude won't be biased toward code it just wrote."
- **Hooks** (deterministic, cannot be talked out of running). *"Hooks are deterministic and guarantee the action happens"* where CLAUDE.md/skill instructions are advisory ([Best practices](https://code.claude.com/docs/en/best-practices); consistent with [claude-code-orchestration-primitives](./claude-code-orchestration-primitives.md) §"Where hooks and CLAUDE.md fit"). Two hook patterns matter specifically for pre-commit gating:
  - A **Stop hook** running a script that must pass before the turn is allowed to end — Claude Code overrides and force-ends the turn after 8 consecutive blocks, so a Stop-hook gate is strong but not infinite.
  - A **PostToolUse hook matched on the commit command itself** — the `security-guidance` plugin's concrete implementation of this is worth reading directly (§4) because it's the only example found that gates specifically on the *commit* action rather than on general edits or session-end.

## 4. Case study: `security-guidance`'s three-layer defense-in-depth

The most fully worked pre-commit review pipeline found — local or in research — is the `security-guidance` plugin (`~/.claude/plugins/marketplaces/claude-plugins-official/plugins/security-guidance/`). It layers three mechanisms of increasing cost and increasing depth, matching review intensity to how far the change has traveled:

1. **Pattern warnings** (cheapest, instant) — regex rules on `PostToolUse` for `Edit|Write|MultiEdit|NotebookEdit`, matching ~25 known-dangerous patterns (`yaml.load`, `pickle.load` on untrusted data, raw `innerHTML`, hardcoded secrets, etc.). Fires on every edit, no LLM call.
2. **LLM diff review** (moderate cost) — on `Stop`, the plugin sends the turn's diff to a separate fast model call and feeds high-severity findings back to Claude *before* the user sees the response, via an `asyncRewake` hook that resumes the agent with a `rewakeMessage` telling it to address or acknowledge the findings.
3. **Agentic commit review** (highest cost, most thorough) — a `PostToolUse` hook matched on `Bash`, gated with `"if": "Bash(git commit:*)"` (and equivalents for `git push`, `gt create/modify/submit` for Graphite users), spins up an SDK-driven reviewer that actually reads related files via `Read`/`Grep`/`Glob` to trace data flow *across* the codebase — catching multi-file classes of bug (IDOR, auth bypass, cross-file SSRF) that single-diff pattern matching structurally cannot see. This is asynchronous and non-blocking (`asyncRewake: true`) rather than a hard gate — it gives feedback rather than preventing the commit outright, which matters: a hard block on `git commit` itself would be a much stronger (and much more disruptive) design choice than what's actually shipped here.

Two governance details worth lifting into any other pre-commit pipeline design:
- **Org-specific policy injection**: a `claude-security-guidance.md` file (three tiers — user, project, project-local) gets concatenated into the review prompt, letting an org encode rules the model can't infer from general training (e.g., "SELECTs against `orders` must go through `db.replica`"). Prompt budget is 8KB; project-local rules truncate first if it overflows, user-wide rules are protected — a deliberate ordering choice about whose rules matter more under space pressure.
- **Explicit non-guarantee**: the plugin's own README states findings are "suggestions, not a substitute for human code review, SAST/DAST, dependency scanning, or pen-testing" — the plugin authors themselves reject the idea that this automation alone constitutes review governance.

## 5. Case study: multi-agent PR review with confidence scoring

Both the `code-review` plugin (`/code-review`, 4 parallel Sonnet agents + Haiku scorers) and `pr-review-toolkit` (`/review-pr`, 6 named specialist subagents) converge on the same structural pattern, independently of each other:

1. **Cheap eligibility gate first** — a small/fast model checks whether review is even warranted (closed/draft/trivial/already-reviewed PR) before spending anything on deep review.
2. **Parallel, role-separated reviewers** — not one generalist pass. `code-review` splits into CLAUDE.md-compliance (×2, deliberately redundant), bug-scan (shallow, diff-only, ignore likely false positives), and git-blame/history context. `pr-review-toolkit` names the roles explicitly: `code-reviewer` (CLAUDE.md + bugs), `silent-failure-hunter` (catch blocks, swallowed errors), `comment-analyzer` (comment/code drift), `pr-test-analyzer` (behavioral test coverage gaps), `type-design-analyzer` (invariant/encapsulation quality), `code-simplifier` (polish, run *after* the review passes, not before — simplification is explicitly sequenced last so it doesn't get reviewed as if it introduced the underlying logic).
3. **Independent confidence scoring as a second pass, not folded into the first** — every raised issue gets re-scored 0–100 by a *separate* agent call against an explicit rubric (0 = false positive/pre-existing, 100 = certain, real, frequent), and only findings ≥80 survive. The rubric bakes in named false-positive classes up front: pre-existing issues, pedantic nitpicks "a senior engineer wouldn't call out," anything a linter/typechecker/CI would already catch, issues explicitly silenced with a lint-ignore comment, and — notably — real issues on lines the PR didn't modify. This is the same shape as the "adversarial review, but scope it or you'll over-engineer" caution in Anthropic's best-practices doc (§3): raising findings is cheap and over-eager by default, so a second, harder-nosed pass has to do the filtering.
4. **The output artifact is a short, cited comment, not a verdict.** Both plugins format results as a single PR comment with linked file+line ranges (full SHA required, several lines of formatting discipline specified) — optimized for a human to scan and decide, not for the automation to gate merge on its own.

Anthropic's own production Code Review product (distinct from these community/example plugins) runs this same shape at larger scale — "dispatches a team of agents... verify bugs to filter out false positives, and rank bugs by severity" — with two details worth noting precisely: it reports **<1% of findings marked incorrect** internally, and it runs **post-commit, on opened PRs, not pre-commit** ([claude.com/blog/code-review](https://claude.com/blog/code-review)). Anthropic is explicit that this is deliberate, not a limitation: *"Code Review won't approve PRs — that's still a human call."* The automation's job is described as making sure "reviewers can actually cover what's shipping," i.e. rationing scarce human attention toward what the automation flags, not replacing the human decision.

## 6. Industry guidance beyond the Claude Code ecosystem

Cross-checked against sources outside Anthropic's own docs/plugins, three independent pieces converge on a consistent picture with Anthropic's own design choices above, which is reassuring corroboration rather than a single vendor's self-serving framing:

- **Risk-tiering, not uniform review** (Osmani, Port.io). Review intensity should scale with *blast radius* (consequences of failure), *code lifespan* (throwaway vs. long-maintained), and *team size* — a config-file typo fix needs a linter, a payments-path change needs full verification, multiple AI reviewers, and named human ownership. Port.io frames the same idea as two gate types: **rule-based** (deterministic, defined ahead of time — e.g. block deploys during a release freeze) vs. **risk-based** (a contextual score — dependency-graph reach, blast radius — that can't be reduced to a fixed rule) ([Port.io](https://www.port.io/blog/human-in-the-loop-for-ai-coding-agents)). Both gate types are stated to depend on a live, accurate view of the system: "a gate that reads stale or partial context makes confident, wrong calls" — a caution that applies directly to any hook or subagent reviewer whose only input is a diff with no broader system awareness.
- **Push structure upstream of the review, not just automation into it** (Osmani). Concrete, repeatable practices: require intent statements, bounded diff size, test output, and CI proof *before* a change is even eligible for human review (pushing reconstruction work onto the author/agent rather than the reviewer); use a cheap "circuit breaker" pass to predict which PRs will be high-maintenance and fast-fail them before spending human attention; keep PRs small — "reviewer engagement is one of the strongest predictors that a PR merges at all"; specifically **scrutinize test changes over implementation changes**, since an agent under pressure to make a check pass has an incentive to loosen the test rather than fix the code, and mutation testing is offered as a check that tests still catch real bugs; and run *heterogeneous* reviewers deliberately — four differently-built review tools in Osmani's data flagged "93.4% of distinct locations by exactly one tool" and "almost none by all four," meaning diversity of reviewer approach finds more real bugs than picking one "best" reviewer and running it twice.
- **Accountability stays human, unconditionally** (Osmani, Anthropic's Code Review page, converging independently): *"A model cannot be paged and cannot be held responsible" — whoever clicks merge owns the outcome.* This is stated as a design principle, not just a legal hedge: it's the reason both the community plugins (§5) and Anthropic's product output a scored, cited *comment* rather than an auto-approval or auto-block.
- **DORA's prescription is process-level, not tool-level**: shift AI-generated feedback to the *author* while they're still writing (not the reviewer after the fact), deploy review agents to enforce standards *before* a human ever opens the diff, enforce small batches structurally rather than by request, and explicitly reconsider whether traditional async review is still the right shape once code-writing speed has changed by an order of magnitude ([DORA — Balancing AI tensions](https://dora.dev/insights/balancing-ai-tensions/)).

## 7. The failure mode automated review doesn't fix by itself: habituation

"Habituation at the Gate" is the one source here in active tension with "just add more automated review agents": it finds human reviewers' approval rates climb and scrutiny falls with repeated exposure to AI-generated code — a rubber-stamping effect that degrades the *human* checkpoint specifically, independent of how good the automated layer in front of it is ([arxiv.org/pdf/2606.22721](https://arxiv.org/pdf/2606.22721)). Read alongside DORA's finding that AI adoption raises throughput and instability simultaneously, the implication is that piling review agents in front of a human who's habituating doesn't obviously fix the underlying quality problem — the automated layer can catch a class of bug, but if the human checkpoint downstream of it is the one that's supposed to catch what automation misses (Anthropic's own framing: "Code Review won't approve PRs — that's still a human call"), and that checkpoint's attention is decaying, the safety property the whole pipeline is designed around gets weaker over time, silently. None of the sources here offer a validated fix; the closest actionable levers surfaced are structural, matching Osmani/DORA's other recommendations above: keep the human's remaining review budget concentrated on genuinely high-blast-radius changes (risk-tiering) rather than spreading thin attention over every PR, and prefer deterministic hooks over "ask the human to remember to look carefully" for anything where habituation-driven failure is unacceptable.

## If you were to design this for a real repo

Combining the enforcement-strength ladder (§3) with the risk-tiering principle (§6) and the habituation risk (§7):

1. **Classify the change's blast radius before choosing how much review it gets** — not "review everything the same amount." Cheap/local/reversible changes (this memo's own repo, `docs`-only edits, config typo fixes) need at most a linter and a skim; anything touching auth, payments, data deletion, or public APIs needs the full stack below plus named human ownership, unconditionally.
2. **Put the cheapest, most mechanical checks in hooks, not prose.** Anything you'd otherwise write as "always run tests before committing" belongs in a `PreToolUse`/`Stop` hook gated on the commit command (`security-guidance`'s `"if": "Bash(git commit:*)"` pattern is a directly reusable template), not as an instruction that can be forgotten under context pressure.
3. **Layer review by cost, matching depth to how far the change has traveled**, mirroring `security-guidance`'s three tiers: pattern/lint on every edit → single-diff LLM review before the turn ends → cross-file, data-flow-tracing agentic review specifically on the commit/push action for anything past the cheap tier.
4. **Make the automated layer produce a scored, cited artifact for a human to act on — never an auto-approval.** Every source here (Anthropic's product, the community plugins, Osmani) converges on the same output shape and the same reasoning: accountability has to stay attachable to a human who can be held responsible, so automation's job is triage (what's safe, what needs a careful look, what's genuinely high-risk) rather than verdicts.
5. **Filter findings with an independent, harder-nosed second pass** before they ever reach a human — the confidence-scoring pattern in §5, with an explicit false-positive taxonomy (pre-existing issues, lint-catchable issues, explicitly-silenced issues, out-of-diff issues) baked into the rubric rather than left to the first pass's judgment alone.
6. **Guard the human checkpoint itself, not just the code in front of it.** Concentrate scarce human review attention on the risk tier that actually warrants it (step 1) rather than diffusing it evenly, since habituation (§7) means uniform, repeated exposure to "mostly fine" AI diffs is itself a failure mode — a reviewer who rubber-stamps 50 low-risk PRs a week has less scrutiny left for PR 51, whatever its risk tier.
7. **Keep changes small and require upstream justification (intent, bounded diff, test output, CI proof) as an eligibility bar for review**, not an afterthought — this does more to keep review effective than adding another reviewer agent to an already-oversized diff.
